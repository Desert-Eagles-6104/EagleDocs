קוד שעובד אצלכם צריך להיות מובן גם למי שיבדוק אותו. **Pull request מציג שינוי, סיבה וראיות, ומאפשר לקבל משוב לפני מיזוג.**

### לא מניחים שהמונחים כבר מוכרים

**ענף (branch)** הוא מסלול עבודה שאפשר לשנות בו קוד בלי להכניס מיד את השינויים למסלול הראשי. **Pull** מקבלת commits שכבר נמצאים במאגר המרוחק. **Pull request — PR** היא בקשה להשוות ענף לענף אחר ולסקור את השינוי לפני שילובו. **Merge — מיזוג** משלב שינוי מאושר. **Conflict — קונפליקט** מופיע כאשר שתי גרסאות שינו אותו מקום ו־Git לא יודעת לבחור לבדה.

המטרה כאן היא לראות ענף עם שינוי שניתן לסקור, לא לבצע מיזוג אוטומטי. קודם שומרים עבודה מקומית וקוראים diff; אחרי זה משתפים.

## 1. פותחים ענף לפני העבודה

ב־VS Code לחצו על שם הענף בשורת המצב ובחרו Create new branch. לדוגמה `training/flywheel-control`. אפשר גם:

```bash
git status
git switch -c training/flywheel-control
```

אם כבר ביצעתם את התרגול בענף האישי הראשי, התחילו שינוי מסכם חדש בענף. אל תשלחו commits לא גמורים לענף הראשי של הקבוצה. מאגר שנוצר מ־Use this template אינו fork: אין להניח שאפשר לפתוח ממנו PR למאגר הקבוצה כמו ממזלג. באימון פותחים PR מהענף האישי לענף הראשי של **אותו מאגר אישי**, ומזמינים מנטור לפי הרשאות. תרומה למאגר הקבוצה תתבצע בהמשך בענף או fork שהקבוצה מאשרת.

### החיווי אחרי יצירת ענף

לחצו על שם הענף **בתחתית חלון VS Code**, בדרך כלל ליד סמל הענף. בתפריט בחרו Create new branch, הקלידו את השם ולחצו Enter. **תוצאה צפויה:** השם החדש מופיע באותו מקום בשורת המצב. אם עדיין מופיע השם הישן, אל תניחו שהענף נוצר — בדקו שוב לפני שינוי.

## 2. שומרים שינוי קטן וברור

פתחו כל diff לפני Stage. ודאו שלא נכללו לוגים, קובצי build, סודות או שינויים לא קשורים של formatter. הודעה כגון `Add flywheel stability check` טובה יותר מ־`fix stuff`. בצעו Push או Publish Branch, ואז ב־GitHub לחצו **Compare & pull request**.

כתבו בתיאור בעברית:

- מה הייתה ההתנהגות הקודמת ומה השתנה.
- איך מריצים את הניסוי, ובאילו קבצים רואים את הלוגיקה.
- טבלת הבדיקות שבוצעו, עם תוצאות בפועל.
- מגבלות: למשל חסר בתבנית, בדיקת חומרה שלא בוצעה או בדיקה חסומה.

### בודקים שה־PR משווה את הענפים הנכונים

לאחר Push, פתחו את המאגר האישי ב־GitHub. אם מופיע Compare & pull request לחצו עליו; אחרת לחצו **Pull requests → New pull request**. בראש הטופס בחרו **base** — הענף שאליו מציעים לשלב, בדרך כלל main — ו־**compare** — הענף האישי שיצרתם. ודאו ששניהם במאגר האישי.

**מה אמורים לראות?** ברשימת Files changed מופיעים הקבצים ששיניתם, עם שורות ירוקות ואדומות כמו ב־diff. קראו אותם לפני Create pull request. אחרי יצירה נפתח דף עם כותרת, מספר PR, תיאור ולשוניות Conversation ו־Files changed. אם כתוב שאין הבדלים, בדקו שנשלחו commits ושבחרתם את compare הנכון; אל תוסיפו שינוי מקרי רק כדי לפתוח PR.

## 3. נותנים ומקבלים סקירה

הסוקר בודק דרישות, עצירה, יחידות, callbacks, קלט ומדידה. הוא שואל ״מה יקרה אם...״ ומנסה לשחזר את הבדיקה. המחבר מסביר, משנה ב־commit נוסף ודוחף לאותו ענף; ה־PR מתעדכן. אין צורך לסגור ולפתוח PR חדש אחרי כל הערה.

### תרגיל סקירה: מה לא נכון פה?

## 4. מתרגלים שיתוף וקונפליקט קטן

בתרגול זוגי במאגר לימודי, שמרו עבודה מקומית וקבלו עדכונים באמצעות Pull. אם שתי גרסאות שינו אותה שורה, VS Code מציגה conflict. קראו את שתי הגרסאות ובחרו את ההתנהגות הנכונה יחד; אל תבחרו Accept Current בכל הקבצים בלי לקרוא. הסירו סימוני conflict, שמרו, בצעו Stage ובנו שוב לפני commit של הפתרון. אם לא ברור מה נכון, עצרו ובקשו סקירה; לא צריך ללמוד rebase כדי לסיים את ההכשרה.

## בדיקת הסיום של ההכשרה

תלמיד אחר משכפל או פותח את ענף הבדיקה, חוזר על ניסוי אחד ומסביר את המסלול מ־`Main` עד המנגנון. אתם מסבירים דרישות, סיום פקודה ומדידה. אחרי אישור, ממזגים לפי נוהל המאגר האישי או הקבוצה — אישור PR אינו אישור לפריסת חומרה.
