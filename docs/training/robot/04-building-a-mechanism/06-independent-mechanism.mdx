עד עכשיו בנינו רולר לפי שלבים והרחבנו את הבדיקה שלו. הפעם מקבלים דרישה למנגנון חדש: **מסוע שמזין שתי מנות בזמנים שונים, עם שחרור קצר לאחור לפני ההזנה.** אין רשימת שורות להעתקה. איך מחלקים את העבודה כך שאפשר יהיה לבדוק כל החלטה?

בסיום תוכלו לעבור מדרישות למנגנון שאפשר להפעיל בסימולציה: לבחור תצורה, לזהות יכולות שכבר קיימות, להרכיב התנהגות ולמסור שינוי שאדם אחר יכול לבדוק. תעבדו בסימולציה עם מנוע אחד ובאחוזי פלט; אין צורך בחיישן, ביעד מהירות או בשיטת בקרה חדשה.

## 1. ניגשים לבעיה לפני שמקלידים

מתחילים מרשימת התנהגויות, ולא ממספר המחלקות שרוצים ליצור. לכל התנהגות כתבו: **מה מתחיל אותה, מה היא מבקשת מהמנגנון, מה מסיים אותה ומה צריך לקרות בביטול**.

כך ניגשים למימוש:

1. **קוראים את הדרישות.** מסמנים מהו נתון קבוע ומהו אירוע בזמן הריצה. אם דרישה אינה ברורה, מנסחים שאלה ממוקדת למנטור לפני חיבור חומרה.
2. **מזהים תצורה ויכולות קיימות.** בודקים את `MotorSubsystemConfiguration` ואת `MotorSubsystemTalon` בגרסה שבפרויקט. הפעלה, ביטול פלט, מדידות ובדיקות יעדים רבות כבר קיימות בבסיס; אין לממש אותן שוב.
3. **מפרטים פעולות.** מפרידים פעולת מנוע אחת מהתנהגות שמורכבת מכמה פעולות. קובעים אילו מופעים של תתי־מערכות כל פעולה דורשת.
4. **בוחרים מימוש.** מחפשים קודם Command קיימת. מתמחים בה אם בחירת קבועים חוזרת ומועילה; משלבים פקודות כשצריך סדר או תיאום; כותבים `Command` חדשה כשיש התנהגות שעדיין לא מכוסה.
5. **מגדירים השלמה וביטול.** לכל שלב יש תנאי סיום; לכל פקודה שמניעה מנוע יש ניקוי גם בהפרעה. זכרו שפקודת אחוזים מהספרייה אינה מסתיימת מעצמה.
6. **מכינים דרך בדיקה.** רושמים בדיקת `Bindings` בתשתית הקיימת, ומכינים בורר, כרטיסי פעולות וטלמטריה ב־Elastic.
7. **בודקים מהקטן לגדול.** תחילה בנייה ונתוני מנגנון ללא הפעלה, אחר כך כל פעולה בפני עצמה, ואז שילוב, ביטול, התנגשות והפעלה חוזרת. משווים תחזית למדידה ומתקנים.

לדוגמה, דרישה ״להפסיק הנעה עכשיו״ אינה סיבה לכתוב `StopMotorCommand` נוספת: אפשר לבדוק אם `MotorSubsystemDisableMotors` מתאימה. לעומת זאת, אם בחרנו לכתוב פקודה חדשה, צריך להסביר מה היא מוסיפה מעבר לפקודות שכבר מצאנו.

### בדיקת תכנון קצרה

תלמיד מתכנן להעתיק אל תת־המערכת החדשה את `getVelocity()`, להפעיל מנוע בבנאי ולסיים רצף באמצעות פקודת עצירה אחרונה בלבד. זהו שלוש בעיות לפני ההרצה, והציעו אחריות מתאימה לכל חלק.

## 2. הפרויקט: TrainingFeeder

`TrainingFeeder` הוא מסוע הזנה חדש שאתם יוצרים, ואינו קיים בתבנית. דמיינו שהוא מקדם חפצי משחק אל תחנת ההמשך. בתרגיל **אין מדידת חפצים**: הפעלה מתוזמנת מדגימה התנהגות, ואינה הוכחה שחפץ באמת עבר.

הרולר מהשיעורים הקודמים נשאר בפרויקט. אין לשנות את תצורתו או את בדיקתו כדי לבנות את ה־feeder. אתם בונים תת־מערכת נוספת ותחברו לה בדיקה נפרדת.

### נתוני ההתחלה לסימולציה

| פרט                | הדרישה                                                              |
| ------------------ | ------------------------------------------------------------------- |
| שם תת־המערכת       | `TrainingFeeder`, כפי שיופיע בלוגים                                  |
| מנוע               | Talon FX אחד, מזהה `53` ברשת `"rio"`; שונה מכל מנוע אימון שכבר נוצר |
| כיוון חיובי        | `counterClockwisePositive = true`                                   |
| מצב נטרול          | `Coast`, נבחר במפורש                                                |
| סוג ומודל          | תנועה `ANGULAR`, עם `DCMotorMechanismSimConfig`                     |
| ערכי המודל הנתונים | מומנט התמד `0.003`, מתח חיכוך `0.1`                                 |
| קדימה              | פלט `0.12` בסימולציה                                                |
| לאחור              | פלט `-0.08` בסימולציה                                               |

אין צורך בחישוב מכני. אלה ערכי מודל וניסוי שסופקו למשימה. מעבר לחומרה דורש מהמנטור כתובת, מגבלות זרם, פלטים ותצורת עמדה מאושרים; החיבור שתבנו כעת ייצור את תת־המערכת בסימולציה בלבד, כפי שעשיתם לרולר.

### התנהגויות נדרשות

| פעולה            | מה מתחיל אותה?           | השלמה וניקוי                                    |
| ---------------- | ------------------------ | ----------------------------------------------- |
| הזנה ידנית קדימה | כרטיס Command ייעודי     | נמשכת עד ביטול או פקודה מתחרה; בסיום מבטלת הנעה |
| שחרור ידני לאחור | כרטיס Command אחר        | נמשכת עד ביטול או פקודה מתחרה; בסיום מבטלת הנעה |
| מנת הזנה כפולה   | הפעלה מפורשת בכרטיס נפרד | מבצעת את הרצף הבא פעם אחת ומסיימת ללא בקשת הנעה |
| עצירה            | כרטיס Stop               | קוטעת פעולה פעילה ודואגת לביטול הנעה            |

רצף **מנת ההזנה הכפולה**, ביחס לרגע תחילתו:

1. לאחור למשך `0.25` שניות כדי להדגים שחרור ראשוני.
2. הפסקת הנעה והמתנה של `0.30` שניות.
3. קדימה למשך `0.80` שניות למנה הראשונה.
4. הפסקת הנעה והמתנה של `0.40` שניות.
5. קדימה למשך `0.35` שניות למנה השנייה, ואז סיום ללא הנעה.

ההתנהגות צריכה להתבצע באמצעות **שילוב של פקודות**. בחרו פקודות מתאימות וחשבו את זמן הסיום הצפוי לפני ההרצה. אל תנהלו את הרצף בעזרת מונה ב־`Robot.teleopPeriodic()` או ב־`Bindings.periodic()`.

ביטול בכל אחד מהשלבים, הפעלת Stop או מעבר ל־Disabled צריכים להפסיק את הפעולה הפעילה ולמנוע את התחלת השלבים העתידיים. ביטול אינו מחזיר חפצים לאחור ואינו מבטל פעולות שכבר קרו. הפעלה מפורשת נוספת מתחילה את המנה **מהשלב הראשון**; אין המשך אוטומטי אחרי Enable.

שתי פעולות של ה־feeder אינן פועלות בו־זמנית. אם מתחילים שחרור ידני בזמן המנה, המנה נקטעת ופקודת השחרור הידני מקבלת שליטה על תת־המערכת לפי מדיניות ברירת המחדל. בדיקת המנוע השני אינה דרישה לפרויקט הזה.

## 3. מתכננים קבצים וחיבורים

לפני המימוש כתבו תוכנית קצרה של המקומות שתשנו. אלה המיקומים המחייבים; תוכן המחלקות ובחירת פקודות הם העבודה שלכם:

| מקום                                                                                | מה צריך להימצא בו?                                                                                                          |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `src/main/java/frc/robot/constants/Constants.java`                                  | מחלקה פנימית `TrainingFeederConstants`, שדה `CONFIG` מטיפוס `MotorSubsystemConfiguration`, וקבועים בעלי שמות לפלטים ולזמנים |
| `src/main/java/frc/robot/subsystems/trainingFeeder/TrainingFeeder.java`             | תת־מערכת שיורשת מבסיס המנוע ומקבלת בבנאי הבסיס את ה־`CONFIG` שלה                                                               |
| `src/main/java/frc/robot/subsystems/trainingFeeder/commands/`                       | רק מחלקות/פונקציות יצירה שיש בהן צורך לפי הבחירה שלכם                                                                       |
| `src/main/java/frc/robot/subsystems/trainingFeeder/TrainingFeederBindings.java` | בדיקת `Bindings` ששולפת את המופע הקיים דרך `RobotContainer.getInstance()` ומפרסמת את הפקודות שלו |
| `src/main/java/frc/robot/RobotContainer.java`                                       | יצירת מופע אחד בסימולציה, שמירתו וקריאה ללוגים שלו                                                                          |
| `src/main/java/frc/robot/TestModeBindings.java`                                     | אפשרות `TRAINING_FEEDER`, זמינה רק כשקיים המנגנון                                                                           |
| `dashboards/training-feeder.json` במאגר האישי                                       | פריסת הבדיקה שתשמרו מ־Elastic                                                                                               |

תנו שמות ברורים לפעולות ולשילוב החיצוני. כדי שחבר יוכל לחזור על הבדיקה, השתמשו במפתחות הבאים לכרטיסים: `Training Feeder/Commands/Forward`, `Reverse`, `Batch` ו־`Stop`, תחת אותה תיקיית `Commands`. אלו פרסומים שתוסיפו; הם אינם מגיעים מהתבנית.

כתבו לצד כל פעולה את הבחירה שלכם - שימוש בספרייה, התמחות, שילוב או פקודה חדשה - ונימוק של משפט אחד. פתרון שמשתמש היטב בפקודות קיימות הוא פתרון מלא. אין דרישה להמציא מחלקה חדשה לכל שורה במפרט.

### תחנה ב: שתי פעולות וכפתור עצירה

ממשו קדימה, לאחור ועצירה, וחברו את הבדיקה ל־`TRAINING_FEEDER`. השתמשו באותו `BindingsManager` ובאותו `/SmartDashboard/Test Mode`. חזרו למסלול Disabled → בחירת בדיקה → Test → Enable.

ב־Elastic הוסיפו את טבלאות הפקודות שיצרתם ואת הנתונים האמיתיים הבאים:

- `/AdvantageKit/RealOutputs/Subsystems/TrainingFeeder/Command`
- `/AdvantageKit/Subsystems/TrainingFeeder/Inputs/AppliedVoltage`
- `/AdvantageKit/Subsystems/TrainingFeeder/Inputs/MechanismVelocityRotPerSec`

בדקו כל כיוון בנפרד, ביטול דרך אותו כרטיס, Stop והתנגשות בין הכיוונים. אין צורך להעתיק שוב מדריך חיבור: השתמשו ב[שיעור Elastic](./04-elastic-testing.mdx#connect-elastic). הבדל בסימן המדידה הוא ראיה לכיוון במודל, ולא אישור לכיוון ההרכבה בחומרה.

## 5. קריטריוני קבלה שאפשר להראות

סמנו סעיף רק אחרי שראיתם את התוצאה, ושמרו ראיה מתאימה. הבנייה מאמתת חתימות ותחביר; גרף וצפייה בהרצה מאמתים התנהגות.

- [ ] הפרויקט נבנה בדרך הרגילה של WPILib ללא שגיאות. תת־המערכת נוצרה פעם אחת בלבד בסימולציה, עם שם וכתובת נפרדים.
- [ ] `TrainingFeederConstants.CONFIG` מכילה את התצורה; הפלטים והזמנים בעלי שמות ונמצאים באותה מחלקת קבועים.
- [ ] בתחילת ההרצה ובכניסה ל־Test אין הנעה בלי בקשת פעולה.
- [ ] קדימה ולאחור פועלות בנפרד, עד ביטול. Stop קוטעת כל אחת ומבטלת פלט.
- [ ] מנת ההזנה מבצעת שחרור, המתנה, מנה ראשונה, המתנה ומנה שנייה, פעם אחת ובסדר הנתון. זמן הסיום תואם את סכום הזמנים בקירוב.
- [ ] אחרי מנה מלאה אין פקודה פעילה ואין בקשת הנעה. הבחינו בין זה לבין מהירות שעשויה עדיין לדעוך.
- [ ] ביטול בכל אחד מחמשת השלבים מנקה את הפעולה הפעילה ואינו ממשיך לשלב הבא. יש תיעוד של לפחות ביטול בזמן תנועה וביטול בזמן המתנה.
- [ ] הפעלת Reverse במהלך Batch קוטעת את המנה, והשחרור הידני הופך לפקודה הנוכחית. הסברתם את התוצאה באמצעות requirements.
- [ ] Disable במהלך מנה מבטל אותה. אחרי חזרה ל־Test אין המשך אוטומטי; הפעלה מפורשת חדשה מתחילה מהשלב הראשון.
- [ ] `TRAINING_FEEDER` נבחרת דרך הבורר הקיים; מעבר לבדיקה וחזרה דרך Disabled מאפשרים להריץ שוב בלי פעולות כפולות.
- [ ] פריסת Elastic כוללת את פעולות הבדיקה, זהות הפקודה והמדידות בנתיבים הנכונים, ונשמרה למאגר האישי.
- [ ] מצורפים צילום של תצוגת המנגנון, גרף של מנה מלאה וגרף ביטול מסימולציה, עם תחזית, תוצאה והסבר קצר לפער אם היה.

לא צריך להגיש ערך מדויק של מהירות סופית או לכוון PID. הראיה הדרושה היא סדר הפעולות, הזמנים, זהות הפקודה וניקוי הפלט. סימולציה אינה מאשרת כתובת או כיוון פיזי של חומרה.

## 6. מוסרים שינוי שאפשר לבדוק

עבדו באותו מאגר אישי. לפני תחילת הפרויקט שמרו את העבודה הקודמת ב־commit, וצרו ענף עבודה כדי להפריד את הפרויקט החדש. **ענף (branch)** הוא קו עבודה בעל שם באותה היסטוריית Git. בטרמינל של תיקיית המאגר אפשר ליצור ולעבור אליו כך:

```bash
git switch -c training/feeder
```

אם כבר התחלתם את העבודה, הפקודה יכולה להעביר לענף החדש גם שינויים שעדיין לא נשמרו ב־commit. בדקו `git status` וקראו את ה־diff לפני Stage, כפי שלמדתם ב[Git ו־GitHub](../01-getting-started/01-git-and-github.mdx).

כתבו תיאור שינוי קצר בעברית שכולל:

- מה המנגנון עושה, ואילו פקודות קיימות בחרתם לשימוש או להרחבה.
- היכן התצורה, איזו אפשרות בוחרים ואילו כרטיסים מפעילים כדי לבדוק.
- אילו בדיקות בנייה וסימולציה ביצעתם, ומה רואים בראיות.
- מה עדיין דורש התאמה ואישור לפני מעבר לחומרה.

שמרו commits שאפשר להבין: למשל חיבור תת־המערכת, ואחריו ההתנהגות והבדיקות. שלחו את הענף למאגר האישי באמצעות **Publish Branch** או Push ב־Source Control. ב־GitHub פתחו **Pull Request** מהענף `training/feeder` לענף הראשי של המאגר האישי, הוסיפו את התיאור והראיות ובקשו מהמנטור סקירה. PR היא בקשה לבדוק שינוי לפני מיזוג; אין למזג אותה לפני הסקירה. כאן לומדים גם למסור קוד, לא רק לגרום למנוע להסתובב.

## לפני שממשיכים

הציגו למנטור דרישה אחת והראו את כל מסלולה: הקבוע המתאים, הפקודה, תנאי הסיום, ה־requirement, כרטיס הבדיקה והראיה מההרצה. הסבירו גם החלטה שבה **בחרתם להשתמש במה שכבר קיים** והחלטה שבה היה צורך להרכיב התנהגות חדשה.

כעת יש לכם תהליך ליישום מנגנון מדרישות, עם פחות הכוונה ועם בדיקה שאפשר לשחזר. בפרק [בקרת מנועים](../05-motor-control/index.mdx) נשתמש במדידה כדי לשמור על מהירות יעד.
