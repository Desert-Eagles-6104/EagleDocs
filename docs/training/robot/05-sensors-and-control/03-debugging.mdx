״המנוע לא עובד״ אינו אבחון. נפרק את השרשרת: מצב → קלט → פקודה → בקשה → מתח → מדידה. בכל שלב נשאל שאלה שאפשר לענות עליה באמצעות נתון.

## 1. סדר בדיקה קצר

1. האם התוכנית נבנתה והתחילה, או שנכשלה לפני `robotInit`? קראו את השגיאה הראשונה ואת ה־stack trace.
2. האם Driver Station במצב המתאים ו־Enabled? בנהיגה: האם נבחר Alliance?
3. האם השלט ביציאה 0 והכפתור או הציר משתנים?
4. האם `Command` מציגה את הפקודה הצפויה? האם פקודה אחרת קטעה אותה?
5. האם הבקשה ביחידות הנכונות, והאם מופיע מתח?
6. האם המדידה מתעדכנת? האם מודל המנגנון מחובר לזירה והטלמטריה מחוברת ל־container?

אם הבנייה נכשלת בהורדת artifact, זו עדיין אינה שגיאת Java שלכם. בדקו חיבור אינטרנט, כתובת המקור וגרסה; אין לבטל בדיקת TLS או למחוק תלויות כדי ״לגרום לזה לעבור״. אם מופיעה `NullPointerException` ביצירת swerve, חזרו ל[מוכנות התבנית](../template-readiness.mdx).

## 2. שלוש תקלות לחקירה

המנטור בוחר שינוי אחד בכל פעם במאגר הלימודי. לפני התיקון רשמו איזו מדידה צפויה לזהות אותו:

- יעד 1200 נכתב במקום 20.
- North הוחלפה ב־`onTrue`, ולכן הפקודה ממשיכה אחרי שחרור.
- קריאת `trainingFlywheel.logTelemetry()` הוסרה, והגרף אינו מציג את inputs.

החזירו את השינוי, הריצו שוב אותו ניסוי ותעדו מדידה לפני ואחרי. אל תשנו גם mapping, גם gain וגם target באותו ניסיון.

### מה לא נכון פה?

תלמיד רואה `TargetRPS = 20`, `MeasuredRPS = 0`, `Command = None` ומחליף את המנוע המדומה. איזו מסקנה מוקדמת הוא הסיק?

## 3. מסבירים תקלה למישהו אחר

כתבו: מה ציפינו, מה ביצענו, מה נמדד, אילו קבצים השתנו ואיך חוזרים על הניסוי. צרפו commit או diff קטן ולוג אמיתי. הסבר כמו ״שיניתי ערך וזה הסתדר״ אינו מספיק אם לא יודעים למה.

לפני עבודה חדשה בצעו Pull במאגר האישי רק אחרי שמירת שינויים מקומיים. פתחו ענף קצר כגון `training/debug-velocity`, ותנו לכל commit סיבה שאפשר להבין מההיסטוריה.
